## 1. 一句话

> **把「数值从哪来」从前端接过去，同时给钱一个去处。**

已有的循环（接单 → 疏导 → 评级 → 名声 → 更重的病人）缺两样东西：

1. **数值是 LLM 写的** —— 升级、刷新申请、诊金定价，全在 `变量更新规则.yaml` 里委托给 AI。玩家感受不到「我在经营」。
2. **钱没有去处** —— `金钱` 只增不减，是个死数字。

本模块做两件事：**把游戏性从前端接回来**（§9 是一张要删的行清单），**把金钱引到物品上**（§6）。

### 1.1 轻度的边界（YAGNI）

明确**不做**（`边境酒馆` 有、我们不要）：

- ❌ 员工系统、任务系统、成就系统、抽奖
- ❌ 多货币与汇率（**单一货币：金钱**）
- ❌ 物品栏与库存管理 —— 买了就摆上，没有「背包」
- ❌ 料理台 / 工作台式的合成
- ❌ 数值上的收支记账表（余额就是余额）

**判断标准**：任何一条如果要求玩家「管理一个列表」，就不做。装修是个例外，因为它是**摆放**不是管理 —— 它给的是空间感，不是工作量。

## 3. 一个等级

**合并 `主角.执业等级` 与 `诊所.星级`。** 用户原话：「执业登记和星级我觉得可以合并，这两个没什么区分的必要」。

```
诊所.等级 ∈ { D, C, B, A, S }         D 为起点，S 为终点
名声 0–100 攒满 → 等级 +1 → 名声清零重算
```

### 3.1 为什么能合并

两者原本都是「你在这一行的分量」，只是**一个面向病人、一个面向同行**。分开时会出现荒谬状态：星级 4 但执业等级 D。合并后只有一个真值，也就不存在不一致。

### 3.2 称号表原样保留

`分档.ts` 里的 `称号表` 正好是五条，与五档一一对应 —— 不用改：

| 等级 | 称号 |
|---|---|
| D | 无名诊所 |
| C | 略有耳闻 |
| B | 小有名气 |
| A | 声名远播 |
| S | **声名鹊起** |

`$称号` 的 transform 从读 `星级` 改为读 `等级`。

### 3.3 删掉的两档

原 schema 是 `F/E/D/C/B/A/S` 七档，新的是五档。**D 成了起点，F 与 E 消失。** 连带要改：

| 文件 | 改什么 |
|---|---|
| `sxmnq/schema.ts` | 三处 `z.enum(['F','E','D','C','B','A','S'])` → `['D','C','B','A','S']` |
| `sxmnq/分档.ts` | `星级称号(星级)` → `等级称号(等级)` |
| `sxmnq/界面/治疗/game.ts` | `等级值` 表的键与值（见 §3.4） |
| `sxmnq/界面/状态栏/结算.ts` | `星级` 读写改 `等级`；`while (名声 >= 100)` 的进位循环保留 |
| `预览/假数据.ts` | **`白露` 与 `陆时` 用了 `'E'`，会静默失败**（safeParse 不过 → 整个 store 退回默认值，界面上只表现为一片默认数字） |
| `世界书/变量/initvar.yaml` | 同步 |

> ⚠ **`'E'` 这个坑值得单独说**：`ts-loader` 是 `transpileOnly`，枚举值写错**不会**在构建时报错；MVU 那边 safeParse 失败是**静默丢弃**。所以假数据里留一个 `'E'` 的表现，是整个预览界面看起来「数据全没了」，而不是报错。改 schema 时这一处必须一起改。

### 3.4 等级值

```ts
const 等级值: Record<等级, number> = { D: 0, C: 1, B: 2, A: 3, S: 4 };
```

**七档改五档，再加闸门，等级差项的实际取值区间变了。** 现有公式：

```
线数 = 污染度 ÷ 8 + (哨兵等级值 − 主角等级值) × 2
```

闸门**两头都在动**，要分开看：

| | 上界 | 下界 |
|---|---|---|
| 闸门限制 | 哨兵不高于诊所 **+1** → 差 ≤ +1 | 低等级永远能来 → 差可以很负 |
| D 级诊所 | 差 ∈ {0, +1} | 只有 D/C 可来，差 ≥ 0 |
| S 级诊所 | 差 ≤ 0（没有更高的了） | D 到 S 全都能来，**差最低 −4** |

**所以该项的实际区间是 −8 到 +2**，不是退化 —— 它是**随等级单调下降**的：越到后期，同一个 D 级病人对你的线数贡献越低。

这正好和 §5.1 是同一个方向的：**等级高了，治低等级的更省力**，小游戏和治疗次数两条线都变轻。而「越级挑战」这一头确实没了（你遇不到比你高一档以上的病人），那是闸门的代价 —— 留作剧情事件的钩子（§4.2），不放进随机池。

作为补偿，**难度差异的另一半由污染度范围承担**（见 §4.2）。系数待实测调。

## 4. 闸门：谁能来

**闸门管的是概率分布，不是准入名单。**

### 4.1 池子

诊所能收到的哨兵等级，**从 D 起，到诊所等级 +1 止**：

| 诊所等级 | 可能来的哨兵 |
|---|---|
| D | D, C |
| C | D, C, B |
| B | D, C, B, A |
| A | D, C, B, A, S |
| S | D, C, B, A, S |

**低等级永远能来**（常客），**每升一档，解锁高它一档的客人**。

### 4.2 权重

```ts
权重(目标档) = 本档 3，每低一档 −1，下限 1；高一档 = 1
```

| 诊所等级 | D | C | B | A | S |
|---|---|---|---|---|---|
| D | 3 | 1 | — | — | — |
| C | 2 | 3 | 1 | — | — |
| B | 1 | 2 | 3 | 1 | — |
| A | 1 | 1 | 2 | 3 | 1 |
| S | 1 | 1 | 1 | 2 | 3 |

读法：**多数是同级的，其次是低一级的，高一级的是稀客。**

> **白塔有、我们暂时不要的尾巴**：白塔的池子允许 1% 的越级来客（D 级诊所也可能撞上 B 级）。本期**不保留** —— 用户明确说「d 的话能有 dc 两种」。但把越级高等级客人做成**剧情事件**（而非随机）是更好的用法，留作后续钩子。

**污染度范围按等级给**（这是难度差异的真正来源，见 §3.4）：

| 等级 | 污染度 |
|---|---|
| D | 20–45 |
| C | 35–65 |
| B | 55–85 |
| A | 70–95 |
| S | 85–100 |

### 4.3 诊金（前序 §12 待定 #2 定稿）

**前端定价**，不再让 AI「给个合理数目」：

```
基础诊金 = (等级值 + 1) × 40 + 污染度 × 2
实际诊金 = round(基础诊金 × 评级系数)       S 1.5 / A 1.2 / B 1.0 / C 0.8
```

| 病例 | 基础诊金 |
|---|---|
| D 级 · 污染 30 | 100 |
| C 级 · 污染 50 | 180 |
| S 级 · 污染 90 | 380 |

评级系数沿用现有 `结算.ts` 的 `收益表`，把它从「乘在诊金上」扩展到「乘在清除量上」（见 §5.3）。

## 5. 治疗次数与床位

用户原话：「拉长哨兵在场的时间，给哨兵一个治疗次数，有了治疗次数，我们就可以有床位」。

### 5.1 单次清除量只跟自己的等级走

```
单次清除量 = 10 + 诊所等级值 × 4         D:10  C:14  B:18  A:22  S:26
实际清除量 = max(1, round(单次清除量 × 评级系数))
```

**注意它不跟病人等级走。** 早期设想过按等级差算，但闸门已经把等级差锁死在一个很窄的区间里（§3.4），差项没有变化空间。改成只读自己的等级。按 §4.2 的污染度范围，预计次数的全表：

| 诊所 | 单次清除 | 治 D 级 | 治 C 级 | 治 B 级 |
|---|---|---|---|---|
| **D** | 10 | 2–5 次 | **4–7 次** | — |
| **C** | 14 | 2–4 次 | 3–5 次 | 4–7 次 |
| **B** | 18 | 2–3 次 | 2–4 次 | 4–5 次 |
| **A** | 22 | 1–3 次 | 2–3 次 | 3–4 次 |
| **S** | 26 | 1–2 次 | 2–3 次 | 3–4 次 |

（格子里的区间是污染度范围内取两端算出来的。区间是闭的，**全表最坏情况是 7 次**。）

正好是用户要的：**「前期我们等级低，治疗等级低的，需要的次数就多，后面我们等级高了，对于低等级的我们治疗效果更好，需要的次数就少了」** —— 治同一个 D 级病人，D 级诊所 2–5 次，S 级诊所 1–2 次。

D 级诊所治 C 级病人要 4–7 次 —— **能治完，但会占床很久**。这是有意的：它让「升到 C 级」这件事的手感非常明确，而不是被闸门挡住。

### 5.2 预计次数与床位占用

```
预计次数 = ceil(污染度 ÷ 单次清除量)       ← 单次清除量未乘系数，即按评级 A（系数 1.0）估
实际次数 = 治到 污染度 ≤ 0 为止            ← 打得好提前出院，打得烂拖长
```

- **预计次数显示在病人卡上**，玩家据此决定接不接 —— 这是「精神力预算」之外的第二个稀缺资源
- 每个**在诊**哨兵占**一张床**，出院/收编即释放
- **床位满时，申请列表可以照常看，但接不了**（按钮置灰 + 一句「没床了」）

**预计次数就是床位占用的天数。** 不设单独的「住院时长」字段 —— 一件事只用一个数表示。

### 5.3 结算改加性

现有 `应用结算` 是**乘性衰减**（`污染度 × (1 − 降幅)`），好处是天然收敛，坏处是**次数不可预测**（玩家没法在接单前知道要几趟）。改为**加性**，代价是 `收益表.污染降幅` 这个字段退役，换成上面的 `评级系数`：

```ts
const 评级系数: Record<评级, number> = { S: 1.2, A: 1.0, B: 0.8, C: 0.5 };
```

`收益表` 的其余三项（名声 / 诊金系数 / 信赖）保留不变。

> **评级第一次有了数值后果之外的意义**：打得烂不只是少拿钱，是**这个病人要多占你两天床**。

## 6. 物品：商店与装修

### 6.1 抽象等级全部删除

前序 §9 的 `诊所.诊室等级` 与 `诊所.躺椅等级` **删除**。用户原话：「不需要躺椅等级、诊室等级这些东西，我们可以只需要让 user 花钱购买提升物品质量就行了」。

改法：**等级 → 具体物品**。一件物品就是**一条结构化效果**：

```yaml
家具:
  床_1:
    名称: 折叠床
    类型: 床                     # 床 | 设施 | 装饰
    氛围: 0
    效果: { 床位: 1 }
```

效果字段（**就这四个，够用为止**）：

| 字段 | 作用 | 旧的对应物 |
|---|---|---|
| `床位` | 同时能住几个 | 无（本期新增，见 §5） |
| `疗效` | 单次清除量 +N | 无 |
| `减耗` | 每场前 N 次失误不计精神力 | 原 `躺椅等级` |
| `氛围` | 气氛值 +N | 无（见 §7） |

一件物品**只有一个效果字段非零**（或全部为零 —— 纯装饰）。不搞组合效果：`疗效 +2 且 氛围 +10` 这种东西会让定价和平衡都变复杂。

### 6.2 商店

**固定货**（写死在卡里）：

| 物品 | 类型 | 效果 | 价钱 |
|---|---|---|---|
| 折叠床 | 床 | 床位 +1 | 300 |
| 诊疗躺椅 | 设施 | 减耗 +1 | 400 |
| 恒温灯 | 设施 | 疗效 +2 | 500 |
| 旧书架 | 装饰 | 氛围 +12 | 100 |
| 素色窗帘 | 装饰 | 氛围 +8 | 60 |
| 助眠香薰 | 装饰 | 氛围 +15 | 120 |

价钱与数值**待调**，先给保守值。定价原则：**一件功能家具 ≈ 3–5 场 D 级治疗的收入**（D 级约 100/场），让第一次升级在一周左右的游戏时间内够得着。

**外接 API 生成**（用户原话：「商店除了我们固定的一些东西，还可以外接 api，让 user 自己生成」）：

- 玩家输入一句描述 → 调 API → 生成一件**装饰品**
- **硬限制：API 生成的物品只能是 `类型: 装饰`，只能给 `氛围`。** 不允许 `床位` / `疗效` / `减耗`
- 理由：API 是外部的、不可控的，**给它游戏性数值就等于把平衡交给了别人**。氛围值是安全的 —— 它只影响信赖加成的一点点（§7），歪了也不破坏循环

详见 §10 的外接 API 一节。

### 6.3 装修：九宫格

用户原话：「点击后出现九宫格，用九宫格来展现楼层和房间的东西南北。每个格子有的固定，比如诊室留出放置床位的格子，有的可以随意安排一些装饰物品放置」。

**一层 = 一个九宫格。** 九个位：

```
西北   北    东北
 西    中     东
西南   南    东南
```

格子分两类：

| 类 | 规则 |
|---|---|
| **预留格** | 位置**写死在房型图里**，只能放对应类型的家具。一层的预留格是 **`中` 与 `南`** —— 两张床位 |
| **自由格** | 其余七格，放任意装饰品（或空着） |

```
一层初始            买到第二张床后
[自][自][自]        [自][自][自]
[自][预][自]   →    [自][床][自]     预留格空了会画一个虚线框 + 「床位」
[自][预][自]        [自][床][自]
```

**床位 = 预留格里实际放了床的数量。** 买了床但没摆 → 不生效，界面上显示「仓库里有 1 张床没摆」（这是唯一的「库存」提示，不是物品栏）。

> **这一块是整个模块最贵的一件。** 九宫格 + 家具渲染 + 拖放/选择 + 多层的数据结构，工作量约等于前面所有部分之和。建议第一版砍到最小：**点击格子 → 弹出可选家具列表 → 选中即放**。不做拖拽。

**多楼层**：数据结构留 `楼层` 维度（`一层` / `二层`…），**第一版只实现一层**。二层靠买「楼梯」解锁 —— 但这条排在最后。见 §13 待定 #3。

## 7. 气氛值

用户原话：「让这些数值不影响游戏性，我们可以开一个别的数值，比如气氛值，这个东西会影响哨兵想要留在这里的进度……这些氛围性的东西会略微影响信任加成」。

```
气氛 = Σ 已摆放家具的 氛围        （未摆放的不算；**本身不封顶**）
信赖加成 = min(5, floor(气氛 ÷ 20))   ← **硬上限 +5**
```

结算时，`信赖加成` **额外加到本次的信赖涨幅上**：

```ts
哨.信赖 = Math.min(100, 哨.信赖 + 信赖加 + Math.min(5, Math.floor(诊所.气氛 / 20)));
```

**上限钉死在 +5，气氛本身不封顶。** 这两件事要分开：

- **气氛不封顶** —— 装饰品可以一直买（§10 的外接 API 就是无限内容源），气氛值一路涨没关系
- **换成信赖的那一步封在 +5** —— 气氛 100 就吃满了，再往上买的纯粹是好看

这是有意的：**不让装饰把百分制的信赖搅膨胀。** 气氛是感情线的**加成**，不是感情线本身。

### 7.1 刻意不做的事

- **不做进度条。** 用户明确说「一切从简」。界面上气氛值只是一个数字 + 一句随档位变的描述（`0–19 有点冷清` / `20–39 还算整洁` / `40–59 待着舒服` / `60+ 让人不想走`）
- **不做衰减。** 摆上去就一直生效，不需要维护
- **不影响申请列表。** 它只跟**已经在场的人**有关 —— 这是感情线，不是拉客手段

**为什么这样切是对的**：气氛值给的是**「我想留住他」的累积感**，而信赖早就在做这件事了。所以它不该是新系统，只该是信赖的**一个缓慢的加成源**。

算一下量级：一个装饰品 +8~15，一层七格自由格摆满约 +70~100 —— **刚好够到 +5 的天花板**。也就是说满装修 ≈ 每次结算多涨 5 点信赖，而信赖本身是 0–100、每次结算涨 1~8。

翻译过来：**满装修把信赖的累积速度抬高一倍左右，然后就不再增长了。** 玩家不会因为买了一屋子摆设就跳过感情线。

## 8. NPC 随机生成：接壤

用户原话：「我还是希望随机生成，因为白塔我们已经有一套成熟的 NPC 随机生成系统可以直接拿过来用了，难点是怎么让他接壤」。

### 8.1 白塔那套本来就有缝

`[哨向]白塔` 的 `固定开启—哨兵邂逅` 已经把它自己的生成**分得很干净**：

| 代码掷（可枚举） | AI 写（自由文本） |
|---|---|
| 等级（`towerPools` 概率池） | **姓名**（附一整套命名法则） |
| 污染度（`pollutionRange`） | 精神体的**具体物种** |
| 年龄（18–35） | 精神体简述 |
| 地域（4 个地域池） | 战损来源 |
| 精神体：纲 × 栖息 × 体型 × 危险（联动掷） | 成文登场描写 |
| 个人特征标签 1–2 个（脸/身/饰/感 四池） | |
| 性格：A 面 + B 面各一个 | |
| 名字要几个字、中式还是西式 | |

**所以「接壤」不是要把两套东西缝起来，是把这个「代码掷」的部分从 EJS 搬到前端 TS。**

要搬的**全是纯数据 + 纯函数**（`weightedPick`、几张权重表、`regionClassMultiplier`），**没有一处依赖酒馆**。搬完前端掷出结果写进变量，AI 照旧读 `变量列表`（它本来就注入整份 `stat_data`）去写文本。

### 8.2 名字归 AI（已定）

用户原话：「名字是很重要的一个东西，如果随便 roll 出来个大壮这种的，玩家会觉得角色没有魅力。AI 通过规则有自己的审美就不会这样」。

**结论：代码掷结构化特征，AI 写名字与文本。** 命名法则（中式要「极简朴素、含偏门姓氏、拒绝古风字眼」那套）从白塔的提示词里提炼后写进我们的世界书条目。

代价是多一层 `待登记` 的状态流转 —— 这正是 §8.4 要解决的。

### 8.3 触发时机

**现在**：AI 在日期变更时清空并重生成 `申请列表`（`变量更新规则.yaml` 里写死的）。

**改后**：前端 watch `世界.日期`（一个 AI 写的字段），变了就掷一批。

### 8.4 iframe 会重建 —— 靠日期戳防重

状态栏 iframe 每次渲染消息都会重建。掷骰逻辑在里面跑，就有重复掷的风险。**解法是给「今天掷过没有」存一个戳**：

```yaml
今日:
  已生成于: '霜降月第一日'      # 日期戳
  待登记: [...]                 # 掷完还没名字的
  申请列表: {}                  # 命名后进来
```

前端流程：

```
iframe 起来（或 watch 到 世界.日期 变了）
  └─ 读 今日.已生成于
      ├─ == 世界.日期  → 什么都不做            ← 解决重建重复掷
      └─ != 世界.日期  → 掷 3–6 个进 待登记，
                         写 已生成于 = 世界.日期
```

**幂等**：无论 iframe 重建多少次、watch 触发多少次，只要戳是今天，就不再掷。

### 8.5 待登记 → 申请列表 → 哨兵

**中间态是真实存在的**（§8.2 选 B 的代价）：掷完到 AI 命名之间，列表里有一批「有数值没名字」的人。

**解法：`待登记` 在界面上显示成「未登记 · 01」**，AI 命名后转正。而转正**不需要逐个匹配** —— 让 AI 一次给全：

> 规则条目里写死：`今日.待登记` 里有 N 个人，**本次回复必须逐一命名、整体写入 `/今日/申请列表/`、清空 `/今日/待登记/`**。

这反而自然：**申请列表本来就是一沓纸**。AI 可以写「桌上那沓申请单」然后一口气把几个人都写出来。

数据流转：

```
待登记[i]  ← 前端掷（等级/污染度/年龄/地域/精神体四属性/特征/性格A面B面）
    │
    │  AI 命名 + 写战损来源 + 写登场
    ▼
申请列表[姓名]  ← 玩家点接诊
    │
    ▼
哨兵[姓名]      ← 在诊（占床）→ 已出院 / 已收编
```

**三个结构的字段必须一致** —— 人是同一个对象在流转，不重新生成。`待登记` 是数组（还没有名字，没法当 key），后两个是以姓名为 key 的 record。

### 8.6 与旧卡的关系

`[哨向]白塔` 是**自家卡**（前序 §2：「旧卡作为素材库保留……需要时取用其世界观、地点、性格池」），因此**直接取用其池子数据是被授权的**。

`边境酒馆经营手札V2.1` 是第三方卡，**只取原理**（`基建度 0–100 → 升级进位` 那个循环），不取文本。

这是本模块的**实质内容** —— 不只是加功能，是把控制权从 AI 手上收回来。现有 131 行里有这些委托：

| 字段 | 现在（AI 干） | 改后 |
|---|---|---|
| `金钱` | 「唯一允许写它的场合：主角掏钱升级诊所设施时扣减升级费用」 | **只由前端买物品时扣。AI 不许动** |

| `申请列表` | 「申请者的等级不超过当前星级解锁的上限」 | **前端池子保证**（§4） |
| `申请列表` | 「诊金按申请者的等级和污染度给个合理数目」 | **前端定价**（§4.3） |

**改后 AI 独占的字段**（它该管的）：`姓名`（NPC 的）、`战损来源`、`世界.日期`、`世界.时段`、`世界.地点`、以及所有文本。

**双方都写的字段**：`世界.日期` —— AI 推进剧情时改，前端只读它来判断该不该掷。

## 10. 外接 API

商店里那一栏「自己生成一件装饰品」。

### 10.1 为什么要外接

固定货是有限的，摆满七格自由格之后装修就没事干了。**外接 API 让装修这件事有无限内容**，而它恰好是唯一一个「多一点内容不会破坏平衡」的地方 —— 因为它只产氛围值。

### 10.2 接哪条线

复用前序 spec §8.3 已有的那条管道（元指令作为 user 消息 → `/trigger` → AI 生成 → 界面读取）。

**但道具生成和剧情生成是两条不同的提示词**，且道具生成**不该污染聊天记录**（玩家会看到一堆「请生成一个台灯」的指令）。所以：

- 走**独立的一次调用**，用完即弃
- 拿到的结果**只存进 `诊所.家具`**，不进聊天
- 失败就退回固定货，不阻塞

### 10.3 受控字段

```ts
// API 只被允许填这几个字段，其余由前端写死
type API产出 = { 名称: string; 描述: string; 氛围: number };
// 类型恒为 '装饰'，效果恒为 {}，价钱由 氛围 反推
```

**前端在写入前把 `类型` 与 `效果` 强制覆写**，不信任 API 的返回。这一层是防错，不是防恶意 —— 但错一次就够把平衡毁掉。

## 13. 执行顺序

用户已定的次序：**① 地基 → ② 商店 → ③ 装修 → ④ 外接 API**。

```
0  修状态栏读错楼层（见 §16）—— 必须在 ① 之前
   ── 这一条不修，申请列表和接诊按钮在真酒馆里根本不可用 ──

① 地基
   1a  schema 改五档 + 删字段，假数据同步（否则预览一片默认值）
   1b  NPC 生成器搬进前端（池子 + 加权掷 + 各属性联动）
   1c  闸门概率池 + 诊金定价
   1d  日期戳与待登记 → 申请列表的流转
   1e  结算改加性，治疗次数 / 床位生效
   ── 到这里，循环闭合，可以跑一局了 ──

② 商店
   2a  家具数据 + 购买（扣钱）
   2b  效果汇总 → 床位 / 疗效 / 减耗 / 气氛

③ 装修
   3a  九宫格渲染 + 预留格（先做「点格子选家具」，不做拖拽）
   3b  摆位 → 气氛重算

④ 外接 API
   4a  生成装饰品的独立调用
   4b  字段强制覆写
```

**1a 必须最先做**，因为等级从七档变五档会让现有的 `假数据.ts` 静默失效 —— 在它修好之前，预览里看到的一切都不可信。

**1b/1c/1d 可以脱机测**（不看 LLM），和前序 M3 的小游戏一样，是能最先摸到手感的部分。

## 16. 附：顺手修掉的坑 —— 状态栏读错楼层

**与经营模块无关，是本来就存在的 bug。** 但 §8.4 的日期戳、申请列表的渲染、接诊按钮全在状态栏里，不修就没法往下做。

### 16.1 现象

`src/sxmnq/` 下有**两个** `defineMvuDataStore`：

| 文件 | variable_option | store id | 读哪一楼 |
|---|---|---|---|
| `界面/共用/数据.ts` | `{ type: 'message' }` → 归一成 `-1` | `mvu_data.-1.message` | **最新楼** |
| `界面/状态栏/store.ts` | `{ type:'message', message_id: getCurrentMessageId() }` | `mvu_data.0.message` | **第 0 楼** |

`util/mvu.ts` 用 `variable_option` 的值拼 store id，所以**两者是不同的 pinia store** —— 两份独立的 `data`、两个独立的 2 秒轮询。

而 `主界面/App.vue` 自己用 `共用/数据`（最新楼），却把用 `./store`（第 0 楼）的 `StatusPanel` 嵌在里面。**同一屏两套数据。**

### 16.2 为什么第 0 楼是错的

`index.yaml:166` 的正则注释写得很清楚：正则没法知道哪条是第一楼，所以**每条消息都会被换成界面**；但「隐藏楼层」脚本把除 0 楼之外的都删掉，**界面只在第 0 楼挂载**（那一楼从头到尾都在，不会被重建，状态才留得住）。

于是 `getCurrentMessageId()` **恒为 0**。

而 AI 的 `<UpdateVariable>` 写进的是**最新楼**。第 0 楼的 `stat_data` 停在 initvar 那一刻。

**后果（真酒馆里，预览里看不见）**：

- 状态栏显示的是**开局冻结状态** —— 名声 0、星级 1、精神力 100、申请列表空
- 玩家点接诊 / 结算 → 全写进第 0 楼那个死 store，剧情那边（最新楼）看不到
- 而同一屏顶部的「待接数」读的是最新楼 → **两个数字对不上**

### 16.3 为什么预览测不出来

`预览/酒馆桩.ts` 的 `getVariables()` **无视传入的 variable_option**，永远返回同一个 `假变量`。所以两个 store 在预览里看起来共享数据，一切正常。

**只有进真酒馆才会发作** —— 这也是它一直没被发现的原因。

### 16.4 修法

删掉 `界面/状态栏/store.ts`，让 `状态栏/App.vue` 改从 `../共用/数据` import。

`共用/数据.ts` 那段注释本来就写着「界面挂死在第一楼不动，变量却要跟着剧情往前跑」，设计意图是明确的 —— `状态栏/store.ts` 违背了它。全项目只有 `状态栏/App.vue` 一处 import 它。

修完，全项目只剩**一个** `defineMvuDataStore` 调用点，同一屏的数字必然一致。
