# 病人入口 · 设计

2026-10-06

## 1. 为什么做

玩家原话：

> 「我需要让正文和前端相呼应，比如现在正文登场了一位需要治疗的哨兵，但是申请治疗里却没有」

### 1.1 现场（有存档，可复查）

存档 `data/default-user/chats/哨向模拟器/哨向模拟器 - 2026-10-06@08h37m03s993ms.jsonl`，
4 条记录，`swipe_id = 0`（**没有重说过**）：

| 楼 | 内容 |
|---|---|
| 1 | 开场白。前端此刻已掷出 6 个人进 `今日.待登记`，`已生成于 = 霜降月第一日` |
| 2 | 玩家：「剧情推进」 |
| 3 | AI：`<game>` 正文里推门进来的那个男人 |

第 3 楼正文里那位 —— 深灰羊绒风衣、暗红头发、金丝半框眼镜、右眼下方泪痣、「穿搭昂贵」
—— 正是 `待登记[0]`：

```
地域: 极东浮岛(商贸物流): …体态匀称具精英松弛感，发色多为高饱和，穿搭昂贵。
特征: ["泪痣", "眼镜(金丝/黑框/半框/圆框)"]
```

逐项对得上，不可能是巧合。AI 的思维链里也写明了：

> 今日待登记的有很多哨兵呢……第一只喵就是极东浮岛的、有泪痣戴眼镜的家伙！
> 我们就安排他作为莉莉今天的第一个病人登场吧喵~

**它看得见那份名单，也是照着那张卡写的正文。**

### 1.2 断在哪

AI 这一楼的 `<UpdateVariable>` 一共 14 条 patch，全是 `世界` / `主角` / `诊所`，
**没有一条碰 `今日.待登记`**：

```
待登记[0].姓名 = ""          战损来源 = ""        （6 个人全是空的）
申请列表 = {}
```

于是 `晋级已命名的()`（`生成/流转.ts:67`）找不到任何有名字的条目 → `申请列表` 空 →
界面显示「今天没有新的申请」+「桌上还压着 6 张没登记的申请单」。

### 1.3 规则没拦住的真正原因

**不是世界书落后。** 本机那份 `data/default-user/worlds/哨向模拟器.json` 里
`[mvu_update]变量更新规则` 是 `disable: false` + `constant: true`（在注入），
且原样含那句「本次回复必须**把 `待登记` 里每一个人都命名完**」。
（探针先自检过：`待登记` / `战损来源` 都命中，不是坏仪表。）

**也不是模型做不到。** 同一份 `<UpdateVariable>` 里，AI 正确写了一条：

```json
{ "op": "insert", "path": "/世界/近期事件/-", "value": { "名称": "极北防线", … } }
```

**追加一条跟本楼剧情有关的记录，它做到了；回填数组某个索引下的两个字段，它没做。**

这不是能力问题，是**动作类型**问题：追加是叙事动作，回填是簿记动作。我们把「给申请者起名」
设计成了后者，还要求它一口气做 6 遍 —— 而那 6 个人玩家一个都还没见过。
`<Analysis>` 模板里那句 *according only to current reply* 也站在它那一边。

**结论：这是设计问题。** 换一个更大的模型可能照做，但那是碰运气，不该留在设计里。

### 1.4 顺带发现的一个洞（本子项目不修，记在这里）

`哨兵[x].状态 = '在诊'` 之后，**没有任何地方能再打开他的治疗面板**：

- `在诊` 在界面上只出现在诊所页那行 `床位 1/2` 的**计数**里，没有名单；
- 申请页的「待接」只看 `申请列表[x].状态 === '待接'`，而结算时会把它改成 `'已接'`
  （`界面/状态栏/结算.ts:271`）—— 从此不再出现。

也就是说 `算预计次数` 那套「一趟治不完、要来回几趟」的设定，**现在没有第二次进门的入口**。
归子项目**乙**。

## 2. 本子项目在三件套里的位置

玩家的完整诉求拆出三件事，各有各的 spec → 计划 → 实施周期：

| | 是什么 | 依赖 |
|---|---|---|
| **甲**（本文） | 病人入口打通：正文登场即转正 + 正文自创的人也能进 | 无 |
| **乙** | 「在诊」变成一个真实的地方：接诊 = 收下 + 占床，治疗另起一个动作（诊所页有病人名单） | 甲 |
| **丙** | 新手教程：开局随机 char，前端主导，串起 加床位 → 入住 → 治疗 | 甲、乙 |

顺序 **甲 → 乙 → 丙**。甲最小、是另外两个的地基，而且它对应的正是玩家报的那个 bug。

## 3. 方案选择

三个走法，都试过对照 1.3 那条证据（追加 vs 回填）：

| | 做法 | 判断 |
|---|---|---|
| 甲-1 | 补丁：规则从「必须命名完 6 个」改成「谁登场给谁填名字」，另加 `今日.新病人` 通道 | 仍然要求 AI 做那个它已经证明自己不做的动作，只是量从 6 降到 1 |
| **甲-2** | **换动作：AI 往 `今日.登场` 追加一条**；前端按 FIFO 把申请单配给他 | **采用** |
| 甲-3 | AI 在 `<game>` 里写 `<登场>姓名</登场>`，前端解析正文 | 已经有 MVU 这条结构化通道，再开一条文本通道是倒退。`界面/主界面/正文适配.ts` 整个文件就是「正文解析能有多脆」的教训 |

**甲-2 采纳的理由**：它让「正文写了谁」和「前端收下谁」变成**同一个动作**，
而不是两个需要对齐的动作。玩家要的「相呼应」是它的副产品，不是需要额外维护的东西。

## 4. 数据流

```
世界.日期 变 ──▶ 前端 掷一批(诊所等级) ──▶ 今日.待登记[3~6]（掷定值，无名字）
                                          UI: 「今天还有 6 个人没露面 · 未到 01…06」

AI 让某人推门 ──▶ <UpdateVariable>  insert /今日/登场/-  { 姓名, 战损来源 }

前端（iframe 起来 / 日期变 / 登场变）──▶ 处理登场()
   逐条：
     待登记 还有剩 ─→ shift() 取最上面那张，用它的掷定值
     没剩了        ─→ 掷一个(诊所等级) 现掷（等级闸门照旧）
     → 申请列表[姓名] = { …掷定值, 战损来源: AI 那句 || 单子里的, 状态: '待接' }
   处理完 今日.登场 = []
```

### 4.1 为什么配对用 FIFO，而不是让 AI 写索引

索引（`用单: 0`）要求 AI 做算术，而且默认值必须选「自创」—— 也就是**它忘了写索引时
所有人都拿不到单子上的样子**，那正是「AI 看着掷出来的卡写正文」这个设计存在的理由，
会静默失效。

FIFO 的默认是「占用最上面那张」，是个**正向的、不用判断的规则**：
AI 这次本来就是自然读了 `待登记[0]` 才写出那段泪痣眼镜的。
`自创: true` 只在罕见情况下标注，**忘了标也不要紧** —— 顶多多用一张单子，不会漏人。

### 4.2 处理时机

`盯住日期` 现在 watch `[世界.日期, 诊所.等级]`。这两者不变时它不重跑，
所以 `处理登场` 不能只挂在那里。

真正让它跑起来的是**每次消息渲染时 iframe 重建**（`immediate: true`）——
现在的 `晋级已命名的()` 本来就依赖这一条。为了不把新逻辑也押在这个假设上，
`盯住日期` 的 watch 源加上第三项：

```ts
watch(
  () => [源.日期(), 源.等级(), JSON.stringify(源.今日().登场)] as const,
  ([日期]) => 跑一次(源.今日(), 日期, 源.等级()),
  { immediate: true },
)
```

**用 `JSON.stringify` 不用 `deep: true`**：MVU 的 `insert` 是就地对数组 `push`，
引用不换，所以必须比内容 —— 但 `deep: true` 会连带深挖 `今日` 底下的
`待登记`（6 条）和 `申请列表`，唤醒次数多过需要。序列化只盯着 `登场` 这一小块，
而且字符串比较走 `Object.is`，内容一样就不会触发。

## 5. 变量契约

### 5.1 `schema.ts`

`今日` 里加：

```ts
// AI 报到的口子：这一楼谁推门进来了。
//
// **它取代了「AI 回填 待登记[i].姓名」那套** —— 见 生成/流转.ts 头部注释。
// 为什么要换：回填数组索引是簿记动作, 追加一条记录是叙事动作, 而后者是 AI
// 本来就在做的事 (它同一条 patch 里正确 append 了 世界.近期事件)。
登场: z
  .array(
    z.object({
      姓名: z.string().prefault(''),
      战损来源: z.string().prefault(''),
      // 罕见：这一楼的人明确不是申请单上的（玩家自己带进来的、你临时加的）。
      // 缺省 false = 占用最上面那张单子。写错也不要紧 —— 顶多多用一张单子。
      自创: z.boolean().prefault(false),
    }),
  )
  .prefault([]),
```

`待登记` 的字段**一个都不删**：

- `字数` / `中式` **留着且仍然有用** —— AI 还是要按它们取名，取名指令从 `待登记`
  那一段搬到 `登场` 那一段。
- `姓名` 留着但不再要求 AI 写。AI 若照老习惯写了，由 6.2 的兼容回路接住。
- 删字段要走老存档迁移，而留着不碍事。

### 5.2 `initvar.yaml`

`今日` 下加 `登场: []`。

理由同 `世界.报纸供稿`：**变量列表注进提示词的是 `stat_data` 本身，不是 schema**
（`世界书/变量/变量列表.txt` 就一句 `{{format_message_variable::stat_data}}`）。
不在这里留位，AI 就看不见这个字段，`登场` 会永远空着 —— 而界面上看起来只是
「今天没有人来」。

### 5.3 `世界书/变量/变量更新规则.yaml`

| 位置 | 现在 | 改成 |
|---|---|---|
| 头部「你独占的字段只有这些」 | `NPC 的 姓名 与 战损来源 (写在 今日.待登记 里)` | `…(写在 今日.登场 里)` |
| 头部「你独占的字段」下一段 | `负责一切需要判断和文笔的东西: 时间推进、给待登记的申请者起名、…` | `…、给登场的人起名、…` |
| `今日.待登记` 的 check | 「**这一块是你唯一要动手的地方**…把 `姓名` 和 `战损来源` 填进去」「本次回复必须把 `待登记` 里每一个人都命名完」 | 「**这一块你只读**。它是今天会陆续来的名单，**从上往下**用：你这一楼让谁登场，就用最上面那张，正文里那个人的样子必须照那一张写」 |
| `今日.申请列表` 的 check | 「由 `待登记` 自动搬进来」 | 「由前端按 `今日.登场` 配好写进去」 |
| — | — | **新增 `今日.登场` 一段**（见下） |

`今日.登场` 那一段要写的三件事：

1. **什么时候写**：这一楼里有哨兵推门进来（或玩家带进来一个人），就给他追加一条。
   一个都没有就不写。
2. **写什么**：`姓名` 和 `战损来源` 两个字段。姓名按**你将要用到的那张申请单**自带的
   `字数` 与 `中式` 取（中式要极简朴素、含偏门姓氏、拒绝言情高频字与古风堆砌；
   西式要平实、避开历史名人与泛滥常见名）。战损来源写具体事件，
   例如「清剿三号污染区时被精神体撕开防线」，不要写「战斗受伤」这种空话。
3. **`自创` 什么时候标**：你写的人明确不是申请单上的（玩家自己带进来的、你临时加的）
   才加 `自创: true`。拿不准就别写 —— 不写等于「用最上面那张」，永远不会漏人。

`申请列表` 那段里「【你】不要自己去写 `申请列表`」**保留** —— 这条一直是对的。

## 6. 前端

### 6.1 `生成/流转.ts`

**先改文件头注释。** 现在 `流转.ts:1-18` 那张图标的是老契约：

```
待登记[i]   ← 前端掷。有数值, 没名字, 界面上显示「未登记 · 01」
   │  AI 写 姓名 + 战损来源  (spec §8.2: 名字归 AI, 因为它有审美)
   ▼
申请列表[姓名]
```

改完之后这条线分岔成两条（AI 报到的 `登场` 是新路，`待登记[i].姓名` 是兼容回路），
旧图会变成一句谎话。**改动本身包含在实施范围内**，不是「顺手更新一下」。

然后新增纯函数，**签名刻意与 `晋级已命名的()` 平行**（同样的入参形状、同样返回 `string[]`）：

```ts
export interface 登场条目 { 姓名: string; 战损来源: string; 自创: boolean }

/** 把 AI 报到的人配进 申请列表。**就地改 今日**, 返回收了谁。 */
export function 处理登场(
  今日: 今日数据,
  诊所等级: 等级,
  随机: 随机源 = Math.random,
): string[]
```

**不返回「现掷了几个」这类计数** —— 没有任何消费者，返回值没人读就是死代码。
测试直接断言被就地改过的 `今日`。

逐字段搬运**照抄 `晋级已命名的` 的写法，不用展开语法** ——
这样 `待登记条目` 以后加字段时这里会**编译不过**，而不是静默漏掉
（这正是 `流转.ts:77` 那条注释在讲的事）。

`流转结果` 加一个字段，与已有的 `晋级` 对称：

```ts
export interface 流转结果 {
  掷了: boolean;
  新掷: number;
  晋级: string[];   // 兼容回路收的 (§6.2)
  登场: string[];   // 新路收的
}
```

`跑一次()` 改成：

```
if (该掷了吗(已生成于, 当前日期)) {
    掷一批 → 待登记
    申请列表 = {}
    登场 = []            ← 新增：昨天残留的报到不该算在今天头上
    已生成于 = 当前日期
    return { 掷了: true, 新掷, 晋级: [], 登场: [] }
}
// 同一天内：
const 晋级 = 晋级已命名的()   ← 兼容回路, 见 6.2。**不删**
const 登场 = 处理登场()       ← 新路
return { 掷了: false, 新掷: 0, 晋级, 登场 }
```

**顺序是先兼容回路、后新路**，有两个理由：

1. 过渡期 AI 可能两套都写（世界书和模型习惯各一半）。先跑老路，新路那条同名报到
   会被 7 节的守卫拦下 —— 结果一致，不会出现「同一个人进两次」。
2. 顺序反过来也不出错，但先老后新时，`处理登场` 看到的 `待登记` 已经是
   `晋级已命名的` 清理过的残表，`shift()` 拿到的必然还没被用过。**顺手省掉一类重叠 bug。**

### 6.2 兼容回路 —— `晋级已命名的()` 为什么不删

我们诊断出的故障，前提之一是「AI 手上那份世界书里有那条规定」。
但**分发出去的卡、别人机器上已经装好的卡，世界书是各自一份** ——
玩家更新卡之前，AI 仍然会照老规矩回填 `待登记[i].姓名`。

留着 `晋级已命名的()`，那些安装照样能出病人。这不是历史包袱，
是**对「提示词契约变更不可能原子生效」这件事的正视**。

**它要加一处改动**：现在是 `今日.申请列表[名] = { … }` 无条件赋值
（`流转.ts:79`），也就是同名后来者覆盖先到者。改成**先到者赢** ——
撞名就跳过并 `console.warn`，与 `处理登场` 用同一条守卫。

这条改动本身很小，但它让两条路的行为一致：不管 AI 走的是老路、新路还是两条都走，
**同一个名字在一批里只进一次**，而且结果与执行次数无关（幂等，见 §9 最后一条）。

### 6.3 `共用/掷骰接线.ts`

`盯住日期` 的 watch 源加上 `今日.登场`（见 4.2）。`跑一次()` 本身是幂等的，
所以多触发只是白跑一遍，不需要防抖 —— 这条性质现有的 `流转.test.mjs` 已经在守。

## 7. 边界

| 情况 | 行为 |
|---|---|
| AI 没写 `登场` | 什么都不发生。界面显示「今天没有新的申请」+「还有 6 个人没露面」 |
| 姓名重复 | 不覆盖已有档案，跳过，`console.warn`。在 `处理登场` 里**不消耗单子**（`shift()` 都不调） |
| 姓名是空串 | 跳过（AI 写半截是常态） |
| 单子用完 | 现掷一个，等级仍走诊所等级闸门 |
| `自创: true` | 不消耗单子，现掷 |
| `自创` 忘了标 | 占用一张单子。不报错、不漏人，只是那个人拿到的细节跟正文描述可能对不上 |
| 跨天 | `跑一次` 清空 `登场` + `申请列表`，重掷 `待登记` |
| 老存档 | `登场` 缺 → prefault `[]`，零迁移 |
| 世界书没同步的老安装 | AI 回填 `待登记[i].姓名` → 兼容回路接住 |

### 7.1 两条路的「重名」处理**故意不同**

同一个词「跳过」，在两条路上的后果不一样，实现时别抄错：

| | 重名时 `待登记` 里那张怎么办 | 为什么 |
|---|---|---|
| `晋级已命名的`（兼容回路） | **丢掉**（从 `待登记` 移走） | 那张单子**本身就是这次报到**。同名说明 AI 把一个人写了两遍 —— 没有第二个人在等着，留着它永远不会有人来 |
| `处理登场`（新路） | **留着**（不 `shift()`） | 那张单子是**一张还没人用的卡**。同名说明 AI 把已经报过到的人又报了一遍 —— 卡该留给下一个真进来的人 |

搞反的后果不对称：兼容回路留着 → `待登记` 永不归零，界面上那行「还有 N 个人没露面」
永远挂着；`处理登场` 丢掉 → 白白烧掉一张掷好的单子，病人少一个。

## 8. 界面

申请页那沓纸的**语义变了**：从「等 AI 命名」变成「候诊中，还没露面」。文案跟着改：

- 「桌上还压着 N 张没登记的申请单」→ **「今天还有 N 个人没露面」**

- **跨天**：日期变 → `登场` 清空

## 10. 不做的事（YAGNI）

- **不做正文解析**。不去正文里找「谁登场了」（甲-3 已否掉）。
- **不改 `申请列表` 的 key 结构**。仍然以姓名为 key。
- **不在本子项目里碰「入住」**。接诊仍然直接进治疗小游戏 —— 那是乙的事。
- **不给 `登场` 加时间戳/序号**。同名同楼重复报到由重名守卫拦住就够了。
- **不删 `待登记` 的 `姓名` 字段**（见 5.1）。
- **不做「AI 没写登场」的自动补救**（比如自动发元指令催）。先看 FIFO 方案的实际发生率，
  真需要再加 —— 玩家说过不要逐步加东西。
